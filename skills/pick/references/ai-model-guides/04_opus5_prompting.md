# 04. Opus 5 プロンプティングガイド（Claude Code 用）

Last verified: 2026-07-25
API model string: `claude-opus-5`（Claude Code では `opus` エイリアスが Anthropic API / Claude Platform on AWS / Bedrock / Google Cloud で Opus 5 に解決。**Microsoft Foundry のみ Opus 4.6** — S94。Opus 5 は Claude Code v2.1.219 以降が必要 — S96）

タグ：`[Official]`（source_id 付き）／`[Heuristic]`（Confidence 付き）

## 1. 公式ポジショニング `[Official]`

- 複雑なエージェント型コーディングとエンタープライズ作業向け。**迷ったらここから始める既定モデル**（S81）。
- Opus 4.8 に対する **step-change improvement**。Fable 5 のフロンティア級知能を**半額**で提供する（S83）。
- 強み：深い推論／エージェント型コーディングと長時間タスク／test-time compute scaling／**低 effort での効率**／コードレビューとバグ発見／vision／long-context／オフィス文書／マルチエージェント統率（S83）。
- **thinking は既定 on**（4.8 は明示設定まで off だった）。`{type:"adaptive"}` は既定と等価。`max_tokens` は thinking と応答の**合計**上限（S84）。
- **`thinking:{"type":"disabled"}` は effort が high 以下のときのみ。xhigh / max との組合せは 400 エラー**（4.8 からの breaking change — S85）。
- effort は5段階すべてに対応、API・Claude Code の既定は high（S71, S72）。**コーディング・エージェント作業は xhigh 開始が公式推奨、その他の知的作業は high**（S86）。max は「タスクが無制限のトークン支出に見合うとき」に上げる（4.7/4.8 の「evals で headroom を確認したときのみ」という明示ゲートは Opus 5 には書かれていない。単純なタスクでは収穫逓減・overthinking の恐れ — S89）。
- 価格 $5/$25 per MTok（4.8 と同額）、1M コンテキスト（既定かつ最大）、最大出力 128k、知識カットオフ 2026-05（S82）。
- **web fetch 非対応・Priority Tier 非対応**（S102）。Fast mode は対応（Claude API のみ・$10/$50 — S103）。
- ZDR：Covered Model の指定はなく、モデル固有の保持要件の記載もない。ただし ZDR 適格性は機能・サーフェス・組織契約に依存するため「全サーフェスで ZDR 可」とは扱わない（S104）。

## 2. このプロジェクトでの最適タスク

- **`[Official]`** 複雑なエージェント型コーディング全般（S81）。難しいコーディング＝複数ファイル機能・大きめのリファクタ・端から端までの実装で最も強く、**スタブやプレースホルダを残さず完遂する**（S83）。コードレビュー・バグ発見（S93）。UI・フロントエンドの視覚的再現（S83）。
- **`[Heuristic]`** 実装の難所、深いデバッグ、UI/UX 実装、Fable 5 を使うほどではないが Sonnet 5 より力が要る局面。 / Confidence: Medium / Basis: S81 の既定ポジション＋コスト（$5/$25）の中間性。

## 3. プロンプティング原則 `[Official]`

- **既存の Opus 4.8 向けプロンプトは箱出しでよく動く**（S92）。まず既定挙動で試し、下の癖が出たときだけ足す。
- **重複する自己検証の指示は入れない。** Opus 5 は言われなくても自己検証・自己修正する。公式が削除を求めているのは次の型：**①最終検証ステップの追加**（「非自明なタスクには最終検証ステップを入れよ」）、**②検証用サブエージェントの起動**（「サブエージェントで検証せよ」）、**③再確認の指示**（「double-check せよ」「答える前に再検証せよ」）。これらは**過剰検証**を招き、品質を上げずにトークンを浪費する（S91）。
- **次の3つは「検証指示」ではないので入れてよい。** 混同しないこと：
  1. **完了定義（受入条件）・通すべきテストの明示** — スコープ定義であり、スコープ拡張の抑制にも効く（S90）。
  2. **根拠の接地の指示**（「推測に頼らずコードから確認せよ」「仮定で済ませるな」）— 事実の裏取りの指示で、重複した検証工程の追加ではない。
  3. **ツール利用の指示**（「スクリーンショットを撮って指定と照合せよ」）— vision タスクでは公式が推奨する使い方（S83）。
- **応答と成果物が長い。** 会話の応答もディスクに書く文書も旧 Opus より長い。簡潔さが要るなら明示指示する（S90）。**effort を下げても表示文は短くならない — 長さはプロンプトで制御する**（S88）。
- **スコープを広げがち。** 頼んでいない手順を足す・タスクの解釈を自分で広げることがある。狭いタスクではスコープを明示的に制約する（S90）。
- **進捗ナレーションが多い。** 望む頻度・形を記述して調整する。正の例が否定指示より効く（S90）。
- **サブエージェント委譲が積極的。** 委譲すべき条件を明示するか、起動数に上限を設ける（S90）。
- **タスク仕様は最初のターンで完全に渡す。** 完全な仕様を先に渡して走らせるのが最も性能が出る（S83, S58）。
- **低 effort を主要なコスト制御手段に。** low / medium は旧 Opus より強い。自分の評価で品質が保てる範囲では積極的に使う。旧モデルの effort 設定を持ち込まず引き直す（S87）。

## 4. 良いプロンプトパターン `[Official]`

- 「ゴール／制約／対象ファイル／完了定義」を第一ターンでまとめて渡す（S83, S58）。字義的なのでパスは正確に書く。
- 簡潔さが要るなら短い指示を1つ入れる。長いシステムプロンプトでは末尾近くに短いリマインダーを添える（S90）。
- 狭いタスクではスコープを明示的に制約する（「頼まれた範囲を、意図された粒度で。ルーチンな判断は自分で行い、解釈で結果が大きく変わるときだけ確認する」）（S90）。
- サブエージェントを使うハーネスでは、委譲の条件と上限を明示する（「本当に独立で大きな作業のときだけ委譲する。自分の作業の検証には使わない」）（S90, S91）。
- max / xhigh effort で走らせるなら max output を 64k から始めて調整（S34）。thinking が既定 on なので、4.8 で thinking なしだった負荷は特に見直す（S84）。
- コードレビューでは全件報告＋信頼度/深刻度を添えさせ、フィルタは下流で行う（S93）。
- vision タスクでは、反復的に解析・crop・目視検証できるツールを与える（S83）。

## 5. 悪いパターン（避ける） `[Official]`

- **重複する自己検証の指示**（「最終検証ステップを入れよ」「サブエージェントで検証せよ」「double-check」「答える前に再検証せよ」）→ 過剰検証。削除する（S91）。※「コードから確認せよ」型の根拠接地の指示は該当しない（上の原則3参照）。
- **旧ハーネスの検証スキャフォールド**（別工程として検証ステップを足すもの）の残置 → 同じ理由で外す（S91）。
- **強制的な進捗要約スキャフォールド**（「3ツール毎に要約」等）→ 望む形を記述する方に置き換える（S90）。
- **曖昧なスコープ** → スコープを広げられる。明示的に制約する（S90）。
- **「冗長にするな」等の抽象的否定** → 正の例・具体的な長さ指定に置き換える（S90）。
- **effort を下げて出力を短くしようとする** → 効かない。長さはプロンプトで指定する（S88）。
- **budget_tokens で thinking を制御** → 400 エラー。effort を使う（S17）。
- **`thinking:{"type":"disabled"}` と effort xhigh / max の併用** → 400 エラー。thinking を有効に保ったまま effort を下げてコストを制御するのが公式の推奨（S85）。
- **「思考するな」「推論するな」系のシステムプロンプト規則** → thinking 無効時に内部 XML タグの漏れを増やす。外す（S85）。

## 6. 再利用テンプレート

**構成は「Fixed instruction / Variables / Output format」の3要素。Opus 5 では Verification 節（＝別工程として検証を指示する節）を置かない**（自己検証は既定挙動であり、明示すると過剰検証になる — S91）。品質の担保は `<done>`（完了定義）で行う。テンプレート内の「コードから確認せよ」型の文は根拠接地の指示であり、削除対象の検証指示ではない。

### 6-1. 実装（難所・高精度）

```md
### Fixed instruction
以下のタスクを、関連実装ファイルを読んでから実装してください。仮定で済ませず、コードベースから
検証できることは検証してください。指定範囲外（<scope_out>）は変更しないでください。
頼まれた範囲を、意図された粒度で実装してください（不要な機能追加・リファクタ・抽象化はしない）。

### Variables
- <task>{{実装したいこと}}</task>
- <files>{{関連ファイルの正確なパス}}</files>
- <scope_out>{{触ってはいけない範囲}}</scope_out>
- <done>{{完了の定義：満たすべき受入条件と、通すべきテスト}}</done>
（推奨: effort=xhigh（コーディングの公式開始点）。max_tokens は 64k から。
 thinking は既定 on なので disabled にしない）

### Output format
1. 実装方針（一文）
2. 差分
3. <done> の各項目に対する結果（テスト/型/ビルドの実行結果を含む）
```

### 6-2. 深いデバッグ

```md
### Fixed instruction
以下のバグの原因を、依存チェーンをたどって特定してください。検索とファイル読み取りを積極的に使い、
推測に頼らずコードから確認してください。原因を確定してから修正案を出してください。

### Variables
- <symptom>{{再現手順と観測される症状}}</symptom>
- <suspected_area>{{当たりがあれば}}</suspected_area>
（推奨: effort=xhigh（エージェント検索の公式開始点））

### Output format
1. 根本原因（一文）
2. 根拠（どのコード・どの経路）
3. 修正案と副作用
```

### 6-3. コードレビュー

```md
### Fixed instruction
以下の差分をレビューしてください。見つけた問題はすべて報告してください（確信が持てないもの・
軽微と思われるものも含む）。この段階で重要度による絞り込みはしないでください。各指摘には
確信度と深刻度を添えてください（フィルタは別工程で行います）。

### Variables
- <diff>{{レビュー対象の差分またはパス}}</diff>
- <context>{{仕様・受入条件・注意してほしい観点}}</context>
（推奨: effort=xhigh。速い一次パスなら low/medium も可 — Opus 5 は低 effort でも精度が保たれる）

### Output format
指摘ごとに：対象ファイル:行 / 内容 / 確信度 / 深刻度 / 修正案
```

### 6-4. UI/UX 実装（開発ツール系）

```md
### Fixed instruction
以下の UI を実装してください。デザイン方向は <design_direction> に厳密に従ってください。
汎用的な「クリーンに」ではなく、指定の配色・タイポ・密度に従ってください。
画像を解析・crop できるツールがあれば、実装後にスクリーンショットを撮って指定と照合してください。

### Variables
- <feature>{{作る画面/コンポーネント}}</feature>
- <design_direction>{{配色・タイポ・余白・密度・参照する既存画面}}</design_direction>
- <constraints>{{使用ライブラリ・アクセシビリティ等}}</constraints>
```

> 6-4 の「スクリーンショットで照合」は**検証指示の例外**：公式が「反復的に解析・crop・目視検証できる
> ツールを与えたとき vision 性能が最も高い」と述べており（S83）、これは自己検証の重複ではなく
> **ツール利用の指示**である。

## 7. 検証チェックリスト（投げる前に）

- [ ] **重複する自己検証の指示**を入れていないか（「最終検証ステップを入れよ」／「サブエージェントで検証せよ」／「double-check せよ」「答える前に再検証せよ」）。※「コードから確認せよ」型の根拠接地は可。（S91）
- [ ] 完了定義（受入条件・通すべきテスト）を `<done>` として明示したか。（S90, S91）
- [ ] スコープを字義的に書いたか（触ってはいけない範囲・「意図された粒度で」）。（S90）
- [ ] 長さ・簡潔さが要るなら明示指定したか（effort では短くならない）。（S88, S90）
- [ ] 進捗更新の頻度・形を指定したか（強制スキャフォールドは外したか）。（S90）
- [ ] サブエージェントの委譲条件・上限を指定したか。（S90）
- [ ] コーディング・エージェント作業なら effort=xhigh を指定したか。（S86）
- [ ] コストを詰めるなら、その作業で low/medium の品質を確認済みか。（S87）
- [ ] max/xhigh なら max_tokens を確保したか（64k〜）。thinking 既定 on を踏まえて見直したか。（S34, S84）
- [ ] `thinking:{"type":"disabled"}` を xhigh/max と併用していないか（400 エラー）。（S85）
- [ ] コードレビューなら全件報告＋下流フィルタの設計にしたか。（S93）
- [ ] 対話型コーディングなら、タスク・意図・制約を最初のターンでまとめて渡したか。（S83, S58）
- [ ] UI なら具体的デザイン方向を指定したか（Opus 5 に既定スタイルの公式記述はないので、方向は自分で与える）。（S83）
- [ ] Claude Code なら effort の現在値を確認したか（**Opus 5 は前回の effort を持ち越す**）。（S97）
