Last verified: 2026-07-25（**Opus 5 対応**：選定対象を Fable 5 / **Opus 5** / Sonnet 5 に更新し、Opus 5 の公式 effort 開始点〈S86。**2026-07-25 の公式改訂で「high 開始・demanding な作業で xhigh へ昇格」に変更**〉・挙動差分〈S90/S91〉・max ゲートのモデル別分離〈S89〉・フォールバック経路〈S98〉・プラン差〈S105/S106〉を反映。旧履歴：2026-07-19 に effort 監査〈S71〜S80〉を反映して第一/第二候補 effort 分離の形式へ再構成、2026-07-09 に判断の土台・分岐へ S67〜S70/P15 を反映、基盤の判断表検証は 2026-07-06）

## 使い方

1. これから行うタスクの行を探す。
2. 第一候補モデルを選ぶ（コスト・速度の制約があれば第二候補へ）。
3. 「指示の型」に従ってプロンプトを組む。詳細な最適化は各モデルの `03/04/05` を参照。

**タグの意味**：`[Official]` = 公式裏付けあり（source_id）。`[Heuristic]` = プロジェクト運用仮説（Confidence 付き、公式裏付けなし）。

**タグ規律の例外**：下の「タスク別判断表」のセルは読みやすさ優先の無タグ要約（Official と Heuristic の混合）。各行の根拠とタグは「タスク別の根拠内訳」セクションが正式に担保する。

## 判断の土台（公式ポジショニング）

- 迷ったら **Opus 5**（複雑なエージェント型コーディング・エンタープライズ作業の既定の出発点）。`[Official]` S81
- 最高能力が要る、人間が数時間〜数週間かける長時間・曖昧・端から端まで → **Fable 5**。`[Official]` S2, S9
- 速い対話・高頻度・低コストの主力 → **Sonnet 5**。`[Official]` S11 ／ 「Fable 5 は速い対話・高頻度には使わない」は公式事実（比較レイテンシ「Slower」・単一リクエスト数分・価格 2 倍 — S10）から導く運用判断。`[Heuristic]` / Confidence: High / Basis: S10 の公式事実。
- **Opus 5 は Opus 4.8 に対する step-change で、Fable 5 のフロンティア級知能を半額（$5/$25 対 $10/$50）で提供する。** 強みは深い推論・エージェント型コーディングと長時間タスク・test-time compute scaling・低 effort での効率・コードレビュー・vision・long-context・マルチエージェント統率。`[Official]` S83
- **model と effort は別の軸（性能ダイヤルの上下ではない）。** model 設定は「どの重みが処理するか」＝おおよそ **how capable（どれだけ有能か）**、effort 設定は「各ターンでどれだけ作業するか」＝おおよそ **how thorough（どれだけ徹底的か）**。effort は「思考時間」だけでなく、ツール呼び出し・応答を含む作業量全体を制御する。`[Official]` S69, S65
- **2 軸は直交する。** 低 effort の大モデルは「専門家に 5 分」（深い経験、ただしざっと読み）、高 effort の小モデルは「優秀なゼネラリストに午後いっぱい」（全部読み、動かし、見直す）。Fable 5 は低 effort でも「一瞥で、他の誰も見抜けない急所を見抜く専門家」。`[Official]` S70 ／ タスクに要るのが**有能さ**か**徹底さ**かを分けて問う（S69, S70 から導く運用指針）。
- **ノブより先に前提を点検する。** Claude が誤ったとき、最初にすべきは model/effort の調整ではなく、渡したコンテキストの点検（プロンプトが曖昧でないか・CLAUDE.md の前提・タスクのスコープ）。不要なはずのタスクで effort を上げているなら、修正はしばしば上流にある。`[Official]` S67
- **ノブを回すなら、まず症状で切り分ける（effort を無条件に先へ上げない）。** ファイルを飛ばした・テスト未実行・見直し不足で誤った → effort を上げる／コンテキストが揃い、明らかに試みたのに誤った → より大きいモデルへ。effort は単一モデル内で知性↔速度/コストを動かせ（low は短い・レイテンシ重視、medium はコスト重視のバランス）、モデル切替より良いレバーであることが多いが、これは切り分けの結果として選ぶもので最上位ルールではない。`[Official]` S6, S65, S68
- **指示は明確・明示的に。** 「上をいく」挙動が欲しいなら明示的に要求する。文脈の乏しい同僚に見せて従えるか、が黄金律。`[Official]` S46
- **effort の既定は high（Claude API・Claude Code とも。`effort:"high"` は省略時と同一挙動）。** `[Official]` S71 ／ モデル別の公式開始点：**3モデルすべて high（既定）開始**。xhigh へ上げる条件がモデルで違う — **Opus 5 は demanding なコーディング・エージェント作業**（S86）、**Sonnet 5 は最難のコーディング/エージェントタスク**（S74）、**Fable 5 は most capability-sensitive な作業**（S75）。`[Official]`
- **effort は default-first。** 大半のタスクはモデル既定の effort を使い、タスクごとの自動ルールではなく作業スタイルの一般選好として調整する（S80）。同名 effort はモデル間で同じ内部強度を意味しない——モデルを替えるなら effort も引き直す（S78）。`[Official]`
- **Opus 5 では低い effort の価値が上がった。** low / medium は旧 Opus より強く、evals で品質が保てる範囲ならトークンコストと応答時間の主要な制御手段として積極的に使ってよい。旧モデルから effort 設定を持ち込まず引き直す。`[Official]` S87
- **Opus 5 では effort を下げても表示される応答は短くならない。** effort が制御するのは思考量。長さはプロンプトで明示指定する。`[Official]` S88

### effort の分岐条件

- **分岐A（Sonnet 5・実装）** `[Heuristic]`：**medium** ＝ 限定された反復作業・既存テストあり・コスト優先（Sonnet 4.6 の high 相当 — S57）／**high** ＝ 複数ファイル・影響範囲不明・検証必要・失敗コスト大。 / Confidence: Medium / Basis: S57・S74 の公式事実＋コスト対効果の運用判断。
- **分岐B（Fable 5 の xhigh 昇格）** `[Heuristic]`：Fable 5 は high で開始する。**要求品質がモデル能力の上限に強く依存し、コスト・レイテンシより能力を優先する場合のみ xhigh へ上げる**。公式の「most capability-sensitive」（S75）の具体的な該当判断は本プロジェクトの運用判断。 / Confidence: Medium / Basis: S75 の公式事実＋案件の重要度判断。
- **分岐C（Opus 5 の xhigh 昇格）** `[Heuristic]`：**Opus 5 は high（既定）で開始する。** xhigh へ上げるのは公式に「**demanding なコーディング・エージェント作業**」とされる範囲（S86）で、本プロジェクトでは次を該当とみなす：**複数ファイルにまたがる実装・大きめのリファクタ・端から端までの機能実装・深い依存チェーンの追跡**（公式が Opus 5 の最も強い領域として挙げる作業 — S83）。**実装・コード調査を伴わない作業（観点整理・批評・方向性検討、小さく閉じたレビュー）は high のまま。**
  **表の読み方**：`high（分岐C で xhigh）` はこの判定を毎回行う行、`xhigh（分岐C）` は行の性質上つねに
  demanding に当たる行（大規模リファクタ・実装の難所・深い依存追跡・大規模監査・長時間自律実行）。 「demanding」の具体的な線引きは本プロジェクトの運用判断。 / Confidence: Medium / Basis: S86 の昇格条件＋S83 の「難しいコーディング＝複数ファイル・大きめのリファクタ・端から端まで」という公式記述。
- **分岐D（Opus 5 の低 effort 活用）** `[Heuristic]`：**自分の評価で品質が保てると確認できている作業**（速い一次レビュー、短い調査、定型的な分類）では low / medium へ下げてよい。公式は「低 effort は旧 Opus より強く、evals で品質が保てる範囲で積極的に使え」「コードレビューの精度は低 effort でも保たれる」と述べる（S87, S93）が、どの作業が該当するかの判断は運用側にある。**未検証のまま常用しない**。 / Confidence: Medium / Basis: S87・S93 の公式事実＋自前評価の要否という運用判断。

### 判断表の effort 設計原則

- 第一候補 effort のうち、モデルの公式**開始点**（3モデルとも high）と一致するセル、および公式が示す**昇格条件に合致するセル**（Opus 5 の demanding なコーディング — S86、Sonnet 5 の最難タスク — S74、Fable 5 の capability-sensitive — S75、low の用途 — S65）は `[Official]` に紐づく。**第二候補 effort の各セルと分岐の該当判断は `[Heuristic]`**（公式はタスク×第二候補の組合せを規定しない） / Confidence: Medium / Basis: S86・S74・S75 の各モデル開始点＋当該行のタスク性質。
- **既定（high）から動かす行には、必ず公式の昇格・降格根拠を紐づける。** 昇格：コーディング・エージェント作業（S86, S74, S75）。降格：evals で品質維持を確認した場合（S87）、短くスコープされた作業・レイテンシ重視（S65）。根拠のない非既定 effort をこの表に置かない。
- この表は「行を引いたときの推奨開始点」であり、対話中にタスクごと頻繁に effort を切り替えることを促すものではない（default-first — S80）。

## 注意（max effort）

- **max は公式の正式レベル**：全対応モデルで「絶対最大能力・トークン支出無制限」、典型用途は「最深の推論と最徹底の分析」。Claude Code では max はセッション限定（環境変数指定を除く）。`[Official]` S76, S77
- **ゲートの表現はモデルで異なる（混同しない）**：
  - **Opus 4.7 / 4.8**：「genuinely frontier problems のために取っておく」「上げるのは **evals が xhigh で measurable headroom を示すときのみ**」。`[Official]` S76
  - **Opus 5**：「**タスクが無制限のトークン支出に見合うときに上げる**」。4.7/4.8 の明示 eval ゲートは Opus 5 のセクションには書かれていない（流用しない）。ただし「単純なタスクでは収穫逓減・overthinking の恐れ」「広範採用前にテスト」は継続。`[Official]` S89
- **本判断表では max をどの行にも置かない**：max は第一推奨にせず、xhigh で headroom を実測した場合の例外昇格として扱う。`[Heuristic]` / Confidence: High / Basis: S76・S89 の公式記述・S77 のセッション限定・S80 の default-first 原則（公式方針と矛盾せず、支持寄り）。

## 注意（refusal リスクとフォールバック）

- **Fable 5 の安全分類器は、攻撃的サイバー技術・生物/生命科学・思考抽出を対象とし、良性のセキュリティ作業や有益なライフサイエンスタスクでも誤検知しうる。** Sonnet 5 も禁止・高リスクなサイバー話題で refusal を返しうる。**Opus 5 も安全分類器を持つ**（Claude Code で自動フォールバックの対象になるのは cybersecurity と biology）。`[Official]` S28, S44, S99
- **Claude Code の自動フォールバックはカテゴリ別**（v2.1.219 以降）：Fable 5 の bio → **Opus 5**、Fable 5 の cyber → **Opus 4.8**、Opus 5 の cyber → **Opus 4.8**、Opus 5 の bio は**フォールバック先がなく refusal で終わる**。`[Official]` S98
- **良性のサイバーセキュリティ作業が拒否されうる領域では、Opus 4.8 を明示選択するのが確実**（フォールバック先として公式に位置づけられており、Active のまま利用できる — S98, S101）。`[Heuristic]` / Confidence: Medium / Basis: S98 のフォールバック経路＋S101 の Active 状態。
- API 利用時のフォールバックはオプトイン（`fallbacks` パラメータ〈beta〉。`"default"` でカテゴリ別の推奨ルーティング）。**Batch API / Bedrock / Google Cloud / Foundry では server-side fallback を使えない**。`[Official]` S29, S100

## 注意（Opus 5 のプロンプト上の癖）

判断表の「指示の型」を補う、Opus 5 固有の注意。詳細は `04_opus5_prompting.md`。

- **重複する自己検証の指示を入れない。** Opus 5 は指示なしで自己検証・自己修正する。公式が削除を求めるのは「最終検証ステップを入れよ」「サブエージェントで検証せよ」「double-check せよ／答える前に再検証せよ」の3型で、これらは過剰検証を招きトークンを無駄にする（品質は上がらない）。**完了定義（受入条件）・通すべきテストの明示、および「推測に頼らずコードから確認せよ」型の根拠接地の指示は残してよい**（いずれも別工程の検証を足すものではない）。`[Official]` S91
- **応答・成果物が長い。** 会話の応答もディスクに書く文書も旧 Opus より長くなる。簡潔さが要るなら明示指示する。`[Official]` S90
- **スコープを広げがち。** 頼んでいない手順を足すことがあるので、狭いタスクではスコープを明示的に制約する。`[Official]` S90
- **委譲・ナレーションが多い。** サブエージェントの委譲条件・上限、進捗更新の頻度と形を指定する。`[Official]` S90

## 迷ったときの分岐（フローの言語化）

0. **直前の出力がうまくいかなかった？** → ノブ（model/effort）を回す前に、渡したコンテキストを点検する（プロンプトの曖昧さ・CLAUDE.md の前提・タスクのスコープ）。修正はしばしば上流にある（S67）。
1. **速い対話 or 高頻度 or 単純？** → Sonnet 5。Fable 5 は使わない（S10 の公式事実に基づく運用判断）。
2. **複雑なエージェント型コーディング or 迷っている？** → Opus 5（S81）。effort は high（既定）から始め、demanding な実装・調査なら xhigh へ上げる（S86、分岐C）。
3. **人間が数時間〜数週間かける、長時間・曖昧・端から端まで？** → Fable 5（S9）。ただしタイムアウト・進捗・フォールバックを事前設計（S25, S29, S98）。
4. **それでも品質が足りない？** → 症状で切り分ける（S68）：ファイルを飛ばした・テストを走らせなかった・見直さなかった → effort を上げる（S6）。関連コンテキストが揃い、明らかに試みたのに誤った → より大きいモデルへ。
5. **コスト・レイテンシを詰めたい？** → Opus 5 なら low/medium が旧 Opus より強い。自前評価で品質が保てることを確認してから下げる（S87、分岐D）。

## 注意（データ保持・ZDR）

**対象範囲**：公式のデータ保持ページが扱うのは Claude API・Claude Platform on AWS・Microsoft Foundry（Anthropic がデータ処理者となるサーフェス）。**ZDR の適用が明示されているのは API の適格機能・条件付きの Claude Code・Claude Platform on AWS**（Foundry は ZDR 適用範囲として明示されていない）。Amazon Bedrock / Google Cloud はクラウド事業者がデータ処理者なので各プラットフォームの資料を見る。`[Official]` S104

- **Fable 5（と Mythos 5）は Covered Model で 30 日データ保持が必須。ZDR では利用不可。** `[Official]` S16, S104
- **Opus 4.8 は ZDR 可**（公式に "remains available under ZDR"）。**Sonnet 5 も ZDR 可**。`[Official]` S104
- **Opus 5 は Covered Model の指定がなく、モデル固有の保持要件の記載もない。** ただし ZDR 適格性はモデルだけでなく利用する API 機能・サーフェス・組織契約に依存するため、「Opus 5 なら全サーフェスで ZDR 可」とは扱わないこと。`[Official]` S104
- 機微データを扱うパイプラインで ZDR 前提のときは Fable 5 を避け、Opus 4.8 / Sonnet 5 を使う。`[Heuristic]` / Confidence: High / Basis: S104 の公式記述。

## 注意（プラン差・Claude Code の運用）

判断表はモデルの適性だけで引く。実際に使えるかは契約プランに依存するため、必要な範囲だけ記す。

- **Fable 5 は全有料プラン（Pro / Max / Team / Enterprise）で選択可能**だが課金形態が違う：**Max / Team Premium 席 / legacy seat-based Enterprise Premium 席はプラン内包**（ただし Fable 5 に使えるのは週間使用量上限の最大 50%）、**Pro / Team Standard 席は usage credits による従量課金**（Enterprise Standard 席は組織が有効化した場合のみ）。**「Pro では使えない」ではなく「usage credits が必要」**。`[Official]` S105
- **アカウント種別の既定モデル**：Max / Team Premium / Enterprise PAYG / API → Opus 5、Pro / Team Standard / Enterprise サブスク席 → Sonnet 5。Fable 5 はどの種別でも既定にならない（`/model fable` で明示選択）。`[Official]` S95
- **Opus 5 は Claude Code v2.1.219 以降が必要。** `opus` エイリアスは同版以降 Anthropic API / Claude Platform on AWS / Bedrock / Google Cloud で Opus 5 に解決（**Microsoft Foundry のみ Opus 4.6**）。`[Official]` S94, S96
- **effort の持ち越しはモデルで違う**：Fable 5 / Opus 4.8 / Opus 4.7 は初回にそのモデルの既定 effort が適用され明示選択まで保持される（default hold）。**Opus 5 にはこの hold がなく、前回設定した effort が持ち越される**ので、実行前に現在の effort を確認する。Sonnet 5 は公式に hold の記載がないため一般の永続規則（low〜xhigh は永続、max はセッション限定）で考える。`[Official]` S97, S77
- **1M コンテキスト**：Sonnet 5 はネイティブ 1M（プラン不問・追加課金なし）。Opus の 1M は Max / Team / Enterprise では自動付与、**Pro では usage credits が必要**。`[Official]` S106

## 注意（Haiku 4.5 について）

このリファレンスは Fable 5 / Opus 5 / Sonnet 5 の 3 モデルに意図的に絞っている。`claude-haiku-4-5`（$1/$5、最速ティア・near-frontier の知能）は対象外 — 単純作業でコスト最小化が最優先の場合は別途検討すること。`[Official]` S66
