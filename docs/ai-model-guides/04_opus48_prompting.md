# 04. Opus 4.8 プロンプティングガイド（Claude Code 用）

Last verified: 2026-07-05
API model string: `claude-opus-4-8`（Claude Code の Anthropic API では `opus` エイリアスが Opus 4.8 に解決 — S49）

タグ：`[Official]`（source_id 付き）／`[Heuristic]`（Confidence 付き）

## 1. 公式ポジショニング `[Official]`

- 複雑なエージェント型コーディングとエンタープライズ作業向け。**迷ったらここから始める既定モデル**（S1）。
- 長時間エージェント作業・ナレッジワーク・視覚・メモリタスクに特に強み（S64）。
- adaptive thinking。manual extended thinking（budget_tokens）は削除済みで 400（S17）。thinking は明示的に `{type:"adaptive"}` を設定しない限り off。
- effort の既定は high（Claude API・Claude Code・claude.ai すべて）。**コーディング・高自律作業は xhigh の明示指定が公式推奨（最良設定）**（S7）。
- 価格 $5/$25 per MTok、1M コンテキスト（既定）、最大出力 128k（S14）。ZDR 利用可（S16）。

## 2. このプロジェクトでの最適タスク

- **`[Official]`** 複雑なエージェント型コーディング全般（S1）、長時間エージェント作業・ナレッジワーク・視覚・メモリ（S64）。
- **`[Heuristic]`** 実装の難所、深いデバッグ、UI/UX 実装、Fable 5 を使うほどではないが Sonnet 5 より力が要る局面。 / Confidence: Medium / Basis: S1 の既定ポジション＋コスト（$5/$25）の中間性。

## 3. プロンプティング原則 `[Official]`

- **極めて字義的。命令を暗黙に一般化しない。** 広く適用したいならスコープを明示（例：「最初のセクションだけでなく全セクションに」）（S30）。
- **応答長はタスクの複雑さに合わせて自動調整。** 特定の長さ・スタイルが要るなら明示する（S31）。
- **長いエージェント実行では定期的・高品質な進捗更新を既定で出す。** 「3ツール毎に要約」等の強制スキャフォールドは外して試す。更新の形が合わなければ望む形を例示（S51）。
- **推論をツールより優先する傾向。** ツール使用を増やすには effort を上げる（high/xhigh で大幅増）か、いつ・どうツールを使うべきかをプロンプトで明示（例：web search を使わないなら、なぜ・どう使うべきか明確に記述）（S32）。
- **サブエージェントは少なめに起動。** 単一応答で完結する作業に起動しない。並列化したいなら明示（S33, S48）。
- **正の例が否定指示より効く。** 望む長さ・深さの応答例を見せる方が「冗長にするな」より確実（S35）。

## 4. 良いプロンプトパターン `[Official]`

- 「ゴール／制約／対象ファイル／完了定義」を第一ターンでまとめて渡し、報告前に検証させる（S64）。字義的なのでパスは正確に書く。
- max/xhigh effort で走らせるなら max output を 64k から始めて調整（サブエージェント・ツール呼び出しの余地を確保）（S34）。
- ツールを使ってほしいのに使わないときは「なぜ・どう使うべきか」を明示（S32）。
- コードレビューで「高severityのみ報告」等の絞り込みを使うなら、全件報告＋信頼度/深刻度を添えさせ、フィルタは下流で行う設計にする（S54）。

## 5. 悪いパターン（避ける） `[Official]`

- **曖昧な指示** → 一般化されず、狭く字義的に処理される（S30）。
- **「冗長にするな」等の抽象的否定** → 正の例に置き換える（S35）。
- **単一応答で足りる作業にサブエージェント指示** → 起動を促しすぎない（S33）。
- **budget_tokens で thinking を制御** → 400 エラー。effort を使う（S17）。
- **汎用的なデザイン否定（「クリームを使うな」「クリーンにして」）** → 別の固定パレットに移るだけ。具体的方向を指定するか複数案を提案させる（S37, S59）。
- **温かい/会話的な声が要るのに指定しない** → 既定は直接的・断定的な文体。必要なら「温かく協調的なトーンで。ユーザーの枠組みを認めてから答えよ」と明示（S36）。
- **強制的な進捗要約スキャフォールド（「3ツール毎に要約」等）の残置** → 既定で高品質な進捗更新を出すため外して試す（S51）。

## 6. 再利用テンプレート

### 6-1. 実装（難所・高精度）

```md
### Fixed instruction
以下のタスクを、関連実装ファイルを読んでから実装してください。仮定で済ませず、コードベースから
検証できることは検証してください。報告の前にテスト・型チェック・ビルドで自己検証してください。
指定範囲外（<scope_out>）は変更しないでください。

### Variables
- <task>{{実装したいこと}}</task>
- <files>{{関連ファイルの正確なパス}}</files>
- <scope_out>{{触ってはいけない範囲}}</scope_out>
- <done>{{完了の定義}}</done>
（推奨: effort=xhigh（コーディングの公式推奨）。max_tokens は 64k から）

### Output format
1. 実装方針（一文）
2. 差分
3. 自己検証の結果（テスト/型/ビルド）

### Verification
<done> の各項目を満たしているか自分でチェックし、満たさない項目があれば明示してください。
```

### 6-2. 深いデバッグ

```md
### Fixed instruction
以下のバグの原因を、依存チェーンをたどって特定してください。検索とファイル読み取りを積極的に使い、
推測に頼らずコードから確認してください。原因を確定してから修正案を出してください。

### Variables
- <symptom>{{再現手順と観測される症状}}</symptom>
- <suspected_area>{{当たりがあれば}}</suspected_area>
（推奨: effort=xhigh（エージェント検索の公式推奨）。ツール使用を増やしたいのでその旨を明示）

### Output format
1. 根本原因（一文）
2. 根拠（どのコード・どの経路）
3. 修正案と副作用
```

### 6-3. UI/UX 実装（開発ツール系）

```md
### Fixed instruction
以下の UI を実装してください。デザイン方向は次を厳密に守ってください（既定の editorial 調ではなく）:
<design_direction> に沿うこと。汎用的な「クリーンに」ではなく、指定の配色・タイポ・密度に従ってください。

### Variables
- <feature>{{作る画面/コンポーネント}}</feature>
- <design_direction>{{配色・タイポ・余白・密度・参照する既存画面}}</design_direction>
- <constraints>{{使用ライブラリ・アクセシビリティ等}}</constraints>
```

## 7. 検証チェックリスト（投げる前に）

- [ ] スコープを字義的に書いたか（「全セクションに」等）。（S30）
- [ ] ツール使用を促す必要はないか（推論偏重の傾向。いつ・どう使うかを明示したか）。（S32）
- [ ] 並列化したいならサブエージェントを明示したか。（S33）
- [ ] コーディング・高自律作業なら effort=xhigh を明示指定したか。（S7）
- [ ] max/xhigh なら max_tokens を確保したか（64k〜）。（S34）
- [ ] 望む長さ・文体を正の例で示したか。（S31, S35）
- [ ] 強制進捗スキャフォールドを外したか。（S51）
- [ ] コードレビューなら全件報告＋下流フィルタの設計にしたか。（S54）
- [ ] 対話型コーディングなら、タスク・意図・制約を最初のターンでまとめて渡したか。（S58, S64）
- [ ] UI なら具体的デザイン方向を指定したか（または複数案提示）。（S37, S59）
