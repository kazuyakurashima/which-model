# 03. Fable 5.1 プロンプティングガイド（Claude Code 用）

API model string: `claude-fable-5-1`

タグ：`[Official]`（source_id 付き, 台帳参照）／`[Heuristic]`（運用仮説, Confidence 付き）

## 1. 公式ポジショニング `[Official]`

- Anthropic の最も高能力な widely released モデル。**Fable 5 の後継**で、長時間のエージェント型コーディング・ナレッジワーク・リサーチを強化。入出力価格は Fable 5 と同額、キャッシュ読みは 1/4（S122, S126）。
- 迷ったら大半のワークロードは Opus 5 から。**demanding reasoning・long-horizon agentic work、または Opus 5 の高 effort でも evals が届かないときに Fable 5.1**（S123）。
- 速度・量のためではない。比較レイテンシは「Slower」で現行ラインナップ中最も遅い位置づけ、価格は Opus 5 の 2 倍（S125）。素早い対話・高頻度タスクに Sonnet 5 を充てるのは、この公式事実から導く運用判断（S125 の結論部は `[Heuristic]` / Confidence: High / Basis: S125 の公式事実〈レイテンシ・価格〉）。
- adaptive thinking が唯一のモードで常時 on。`thinking:{type:"disabled"}` は非対応で **400 error** を返す。手動 extended thinking も同様（S8）。
- 生の思考連鎖は決して返らない（`thinking.display` 既定は "omitted"。可視化は "summarized"、進捗更新だけなら "updates"〈beta〉— S20）。
- 30 日データ保持必須・ZDR 不可・Covered Model 指定（S127）。価格 $10/$50 per MTok、キャッシュ読み $0.25/MTok（S126）。

## 2. このプロジェクトでの最適タスク

- **`[Official]`** 数時間走るエージェントセッション・多段の deep research・完成した文書/スプレッドシート/デッキまで持っていく分析（S123）。能力向上は6領域に集中：長時間セッションのコーディング（複数ファイル機能・大規模リファクタ/移行・デバッグ・コードレビュー）、文書・スプレッドシート・スライド、リサーチと検索、vision、long-context、computer use — **差は高 effort ほど大きい**（S124。公式ベンチマークの値は S143）。Claude Code で一度に収まらない大きなタスク（S138）。
- **`[Heuristic]`** アプリ初期設計、要件定義、大規模リファクタ、独立した目でのコードレビュー。 / Confidence: Medium / Basis: S123・S124 の位置づけ＋プロジェクトの重要局面。

## 3. プロンプティング原則 `[Official]`

既存の Fable 5 プロンプトは**変更なしで 5.1 でも良好に動く**のが公式の前提（S133）。以下の原則は Fable 5 から引き継ぎ、5.1 の挙動差（S134）を追記する。

- **ゴールと理由を与える。逐一チェックリストにしない。** 一般的な指示が手書きプランより良い推論を生むことが多い（S47）。指示追従は強いので短い指示でよい（S26）。
- **難易度レンジの上端から始める。** 旧モデルより難しいタスクを与え、スコープ確認・質問・実行をさせる（S21）。
- **検証の指示は「長時間・自律実行」に限る（適用条件に注意）。** Claude Code の公式ガイダンスは
  「Fable 系は少ない指示で自分の作業を検証するので、テストや確認のリマインダーは**通常不要**」とする一方、
  prompting ガイドは**長時間実行では**自己検証を明示せよ（別コンテキストの検証サブエージェントが
  自己批判より優れる）とする。両者は矛盾ではなく適用条件が違い、**5.1 でも方向逆転はない**（S22）：
  **通常タスク → 検証リマインダーを入れない／長時間・自律実行・進捗の信頼性が要る作業 → 検証方法と
  間隔、別コンテキストの verifier を構造化して指定する。**
- **境界を明示する。** 高 effort での不要な整頓・リファクタ・過剰な抽象化を防ぐため「タスクに必要な以上のことはするな」と書く（S24）。
- **過剰計画を抑える。** 「行動できる十分な情報があれば行動せよ」（S23）。
- **旧モデル向けの過剰指示を削除する。** 既定挙動で十分なら消す（S26）。**5.1 では特に：アンチ書式指示（bold・リスト禁止系）と「発見を最終応答まで貯めろ」系の指示は逆効果になりうるので削除・置換する**（S134 ②⑤）。
- **複雑な非同期ワークロードでは「ターンを終える前に作業を終えよ」と促す。** 促さないと「次は〜します」と述べて止まる・依頼済みの手順に許可を求めることがある。公式の2ブロック（自律動作の宣言＋依頼スコープ＝成果物の定義）を使う。冒頭の「ユーザーはリアルタイムで見ていない」の1文が効果の大半（S135）。
- **サブエージェントへの委譲を抑制しない。** 並列委譲は信頼できるので「いつ委譲すべきか」を明示し、委譲後は非同期に（spawn-and-block ではなく）作業を続けさせる（S55）。ハーネス側も lead を完了待ちでブロックしない設計にすると平均完了時間が下がる（S137）。
- **長時間タスクの進捗報告は接地させる。** 報告前に各主張をセッション内のツール結果と突き合わせて検証させると、捏造ステータス報告がほぼ解消する（S56）。

## 4. 良いプロンプトパターン `[Official]`

- 大きなドキュメント（コードベース・仕様・原稿）はプロンプト上部・指示より前に置き、XML タグで区切る（例：`<codebase>…</codebase>`, `<spec>…</spec>`）。全モデル共通の原則（最大 30% の品質向上）で、入力が大きくなりがちな Fable 5.1 のタスクでは特に効く（S61）。
- 長時間作業では Markdown のメモファイルを持たせる：1 ファイル 1 教訓、先頭に 1 行要約、重複せず更新、誤りは削除（S62）。
- 逐語で見せるべき内容には `send_to_user` 型ツールを用意し、システムプロンプトで「ユーザーが逐語で読むべき内容のときに呼べ。ナレーションや内部推論には使うな」と明示する（S27）。
- 最終応答のスタイルを別途指定：結論を先に、次に根拠。作業用の省略記号・矢印連鎖・内部ラベルをユーザーに出さない（S63）。
- **エージェントループで1ターン1ツール呼び出しになったら**、「必要なものを列挙し、互いに依存しないものはこの1応答でまとめて要求せよ」の1行を足す（5.1 は次の独立呼び出しが暗黙のとき並列化が不安定 — S134 ①）。
- **進捗テキストが少なすぎるとき**は、「開始時に一言・作業中は短い更新・最後に単独で読める要約」を明示的に頼む（5.1 は既定の進捗ナレーションが Fable 5 より少ない — S134 ②）。

## 5. 悪いパターン（避ける） `[Official]`

- **「思考を出力せよ」「推論を段階的に説明せよ」「内部推論を繰り返せ」** → 5.1 の安全分類器は Fable 5 と同じカテゴリ構成で、reasoning_extraction 拒否を誘発しうる（S131, S99）。可視化が要るなら `thinking.display:"summarized"`（進捗更新だけなら `"updates"`〈beta〉）を読む設計に（S20）。※フォールバックは API ではオプトイン設定（`fallbacks`〈beta〉。`"default"` でカテゴリ別の推奨ルーティング — S100）。**5.1 の許可フォールバック先は Opus 4.8 と Opus 5**（S131）。**Claude Code ではカテゴリ別に自動フォールバックが働く：bio → Opus 5、cyber → Opus 4.8**（S98）。
- **短い対話でチャットのように使う** → 比較レイテンシ「Slower」で高価（S125）。速い対話には Sonnet 5 を充てる（S125 由来の運用判断）。
- **xhigh / max で長い成果物を一発生成させる** → 成果物を thinking 内で下書きしてから書き直し、待ち時間と出力トークンが倍増しうる。high で走らせるか、公式の注記スニペットを付ける（S136）。
- **攻撃的サイバー技術・生物/生命科学・思考抽出に触れる依頼** → 安全分類器の対象（S131）。誤検知は Fable 5 のローンチ時より減り、**ソースコードの脆弱性発見は許可されている**が、コンパイル確認の言い回し・マイナー言語・ツール出力中の base64 では誤検知が起きやすい（S132）。該当が予想されるタスクは、サイバー系なら **Opus 4.8**（公式のフォールバック先で Active のまま利用可 — S98, S101）、生物・生命科学系なら **Opus 5**（Claude Code では bio 拒否時のフォールバック先。ただし Opus 5 自身も bio 分類器を持ち、その場合はフォールバックなしで refusal になる — S98）を検討する。
- **forced tool use（`tool_choice: any / tool`）を渡す** → 5.1 では 400 エラー。スキーマ強制は strict tool use か structured outputs へ。過去ターンを編集して再送するハーネスも thinking ブロック無効化で 400 になりうる（Claude Code は対応済み — S139）。

## 6. 再利用テンプレート

各テンプレートは **Fixed instruction / Variables / Output format** を基本とし、
**`Verification` 節は長時間・自律実行のタスクにだけ付ける**（短く閉じたタスクでは省く — S22 の適用条件）。

### 6-1. 設計レビュー依頼

```md
### Fixed instruction

あなたは経験豊富なソフトウェアアーキテクトです。以下の文脈を読み、ゴールを達成する設計を
自分でスコープし、必要なら明確化のための質問をしてから実行してください。逐一の手順は指定しません。
必要以上の機能追加・抽象化はしないでください。作業できる十分な情報があれば進めてください。

### Variables

- <goal>{{達成したいこと}}</goal>
- <constraints>{{技術・期限・非機能などの制約}}</constraints>
- <codebase>{{関連ファイル群。大きなものはここに上部配置}}</codebase>
- <decision_needed>{{今回決めたい論点}}</decision_needed>

### Output format

1. 結論（採用する設計方針を一文で）
2. 根拠（トレードオフを含む）
3. 主要な決定事項
4. リスクと未確定事項

### Verification（長時間・自律実行の場合のみ付ける）

最終案について、別のサブエージェント（別コンテキスト）に「この設計が壊れる条件」を検証観点として
列挙させ、それぞれに対処するか、未対処なら明示させてください。
```

> 短時間で終わる設計相談では上の `Verification` 節を省く。Fable 5.1 は少ない指示で自己検証するため、
> 通常タスクでの検証リマインダーは不要（S22 の適用条件）。

### 6-2. 大規模リファクタ／移行

```md
### Fixed instruction

以下のリファクタを、影響範囲調査 → 計画 → 実装 の順で進めてください。既存テストスイートを合否基準とし、
変更はテストが通ることを都度確認してください。指定範囲外は変更しないでください。
タスクに含まれない箇所の修正・最適化・拡張はしないでください（気づいたことは最後に報告として挙げる）。

### Variables

- <target>{{リファクタ対象と目的}}</target>
- <scope_in>{{変更してよい範囲}}</scope_in>
- <scope_out>{{触ってはいけない範囲}}</scope_out>
- <success_criteria>{{完了の定義。通すべきテスト等}}</success_criteria>

### Output format

1. 影響範囲サマリ
2. 実行計画
3. 差分（段階ごと）
4. テスト結果

### Verification（長時間・自律実行の場合のみ付ける）

実装後、別のサブエージェント（別コンテキスト）に差分と success_criteria を突き合わせさせ、
要件を満たさない箇所を報告させてください。
```

## 7. 検証チェックリスト（投げる前に）

- [ ] このタスクは Fable 5.1 に値するか（長時間・複雑・端から端まで）。単純なら Sonnet 5 へ、複雑なエージェント型コーディングなら Opus 5 も検討。（S123, S125）
- [ ] 「思考を説明せよ」系の文言が残っていないか。（S131）
- [ ] ゴールと理由を与えたか。逐一チェックリストになっていないか。（S47）
- [ ] **長時間・自律実行なら**検証手段（テスト・受入基準・検証サブエージェント）を用意したか。**短く閉じたタスクなら逆に検証リマインダーを入れていないか。**（S22）
- [ ] タイムアウト・進捗表示・refusal フォールバックを事前調整したか。（S25, S131）
- [ ] 機微データで ZDR 前提なら Fable 5.1 を避けたか。（S127）
- [ ] サブエージェントへの委譲を「いつ使うか」明示し、非同期に進める設計にしたか。（S55, S137）
- [ ] 長時間タスクなら、進捗報告をツール結果と突き合わせて検証させる指示を入れたか。（S56）
- [ ] 旧モデル向けのアンチ書式指示・「報告を貯めろ」系の指示を持ち込んでいないか。（S134）
