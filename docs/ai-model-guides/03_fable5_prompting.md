# 03. Fable 5 プロンプティングガイド（Claude Code 用）

Last verified: 2026-07-06
API model string: `claude-fable-5`

タグ：`[Official]`（source_id 付き, 台帳参照）／`[Heuristic]`（運用仮説, Confidence 付き）

## 1. 公式ポジショニング `[Official]`

- Anthropic の最も高能力な一般提供モデル。長時間稼働エージェント向けの次世代知能（S3）。
- 人間が数時間・数日・数週間かける端から端までの作業に特に効果的。簡単なワークロードだけで試すと真価を過小評価する（S9）。
- 速度・量のためではない。比較レイテンシは「Slower」で単一リクエストが数分に及ぶ（S10）。素早い対話・高頻度タスクに Sonnet 5 を充てるのは、この公式事実から導く運用判断（S10 の結論部は `[Heuristic]`）。
- adaptive thinking が唯一のモードで常時 on。`thinking:{type:"disabled"}` は非対応（エラーで拒否）（S8）。
- 生の思考連鎖は決して返らない（S19）。
- 30 日データ保持必須・ZDR 不可・Covered Model 指定（S16）。価格 $10/$50 per MTok（S13）。

## 2. このプロジェクトでの最適タスク

- **`[Official]`** 大規模移行・多段分析・複雑なエージェントフロー・横断的リサーチ・高精度な視覚理解（S9）。Claude Code で一度に収まらない大きなタスク（S50）。
- **`[Heuristic]`** アプリ初期設計、要件定義、大規模リファクタ、独立した目でのコードレビュー。 / Confidence: Medium / Basis: S9 の位置づけ＋プロジェクトの重要局面。

## 3. プロンプティング原則 `[Official]`

- **ゴールと理由を与える。逐一チェックリストにしない。** 一般的な指示が手書きプランより良い推論を生むことが多い（S47）。Fable 5 の指示追従は強いので短い指示でよい（S26）。
- **難易度レンジの上端から始める。** 旧モデルより難しいタスクを与え、スコープ確認・質問・実行をさせる（S21）。
- **長時間タスクでは自己検証を明示。** 別コンテキストの検証サブエージェント（Task ツール等での別実行）が自己批判より優れる（S22）。
- **境界を明示する。** 高 effort での不要な整頓・リファクタ・過剰な抽象化を防ぐため「タスクに必要な以上のことはするな」と書く（S24）。
- **過剰計画を抑える。** 「行動できる十分な情報があれば行動せよ」（S23）。
- **旧モデル向けの過剰指示を削除する。** 既定挙動で十分なら消す（S26）。
- **サブエージェントへの委譲を抑制しない。** 並列委譲は信頼できるので「いつ委譲すべきか」を明示し、委譲後は非同期に（spawn-and-block ではなく）作業を続けさせる（S55）。
- **長時間タスクの進捗報告は接地させる。** 報告前に各主張をセッション内のツール結果と突き合わせて検証させると、捏造ステータス報告がほぼ解消する（S56）。

## 4. 良いプロンプトパターン `[Official]`

- 大きなドキュメント（コードベース・仕様・原稿）はプロンプト上部・指示より前に置き、XML タグで区切る（例：`<codebase>…</codebase>`, `<spec>…</spec>`）。全モデル共通の原則（最大 30% の品質向上）で、入力が大きくなりがちな Fable 5 のタスクでは特に効く（S61）。
- 長時間作業では Markdown のメモファイルを持たせる：1 ファイル 1 教訓、先頭に 1 行要約、重複せず更新、誤りは削除（S62）。
- 逐語で見せるべき内容には `send_to_user` 型ツールを用意し、システムプロンプトで「ユーザーが逐語で読むべき内容のときに呼べ。ナレーションや内部推論には使うな」と明示する（S27）。
- 最終応答のスタイルを別途指定：結論を先に、次に根拠。作業用の省略記号・矢印連鎖・内部ラベルをユーザーに出さない（S63）。

## 5. 悪いパターン（避ける） `[Official]`

- **「思考を出力せよ」「推論を段階的に説明せよ」「内部推論を繰り返せ」** → reasoning_extraction 拒否カテゴリを誘発し、Opus 4.8 へのフォールバックが増える（S19）。可視化が要るなら `thinking.display:"summarized"` を読む設計に（S20）。※フォールバックは API ではオプトイン設定（`fallbacks`〈beta〉）。Claude Code では分類器フラグ時に自動モデルフォールバックが働く（S29）。
- **短い対話でチャットのように使う** → 比較レイテンシ「Slower」で高価（S10）。速い対話には Sonnet 5 を充てる（S10 由来の運用判断）。
- **簡単なタスクだけで評価する** → 真価を過小評価（S9）。
- **攻撃的サイバー技術・生物/生命科学・思考抽出に触れる依頼** → 安全分類器の対象（S28）。**良性のサイバーセキュリティ作業や有益なライフサイエンスタスクでも誤検知で refusal を返しうる**。該当が予想されるタスクは Opus 4.8 を検討する。

## 6. 再利用テンプレート

各テンプレートは **Fixed instruction / Variables / Output format / Verification** の 4 部構成。

### 6-1. 設計レビュー依頼

```md
### Fixed instruction

あなたは経験豊富なソフトウェアアーキテクトです。以下の文脈を読み、ゴールを達成する設計を
自分でスコープし、必要なら明確化のための質問をしてから実行してください。逐一の手順は指定しません。
必要以上の機能追加・抽象化はしないでください。作業できる十分な情報があれば進めてください。

### Variables

- <goal>{{達成したいこと}}</goal>
- <constraints>{{技術・期限・非機能などの制約}}</constraints>
- <codebase>{{関連ファイル群。大きなものはここに上部配置}}</codebase>
- <decision_needed>{{今回決めたい論点}}</decision_needed>

### Output format

1. 結論（採用する設計方針を一文で）
2. 根拠（トレードオフを含む）
3. 主要な決定事項
4. リスクと未確定事項

### Verification

最終案について、別のサブエージェント（別コンテキスト）に「この設計が壊れる条件」を検証観点として
列挙させ、それぞれに対処するか、未対処なら明示させてください。
```

### 6-2. 大規模リファクタ／移行

```md
### Fixed instruction

以下のリファクタを、影響範囲調査 → 計画 → 実装 の順で進めてください。既存テストスイートを合否基準とし、
変更はテストが通ることを都度確認してください。指定範囲外は変更しないでください。

### Variables

- <target>{{リファクタ対象と目的}}</target>
- <scope_in>{{変更してよい範囲}}</scope_in>
- <scope_out>{{触ってはいけない範囲}}</scope_out>
- <success_criteria>{{完了の定義。通すべきテスト等}}</success_criteria>

### Output format

1. 影響範囲サマリ
2. 実行計画
3. 差分（段階ごと）
4. テスト結果

### Verification

実装後、別のサブエージェント（別コンテキスト）に差分と success_criteria を突き合わせさせ、
要件を満たさない箇所を報告させてください。
```

## 7. 検証チェックリスト（投げる前に）

- [ ] このタスクは Fable 5 に値するか（長時間・複雑・端から端まで）。単純なら Sonnet 5 へ。（S9, S10）
- [ ] 「思考を説明せよ」系の文言が残っていないか。（S19）
- [ ] ゴールと理由を与えたか。逐一チェックリストになっていないか。（S47）
- [ ] 長時間なら検証手段（テスト・受入基準・検証サブエージェント）を用意したか。（S22）
- [ ] タイムアウト・進捗表示・refusal フォールバックを事前調整したか。（S25, S29）
- [ ] 機微データで ZDR 前提なら Fable 5 を避けたか。（S16）
- [ ] サブエージェントへの委譲を「いつ使うか」明示し、非同期に進める設計にしたか。（S55）
- [ ] 長時間タスクなら、進捗報告をツール結果と突き合わせて検証させる指示を入れたか。（S56）
