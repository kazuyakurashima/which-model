## 使い方

1. これから行うタスクの行を探す。
2. **通常推奨**を既定の開始点とする。目的がはっきりしているときだけ、**成果優先**（コストと待ち時間を評価から外す）または**効率優先**（必要品質を保てる範囲で総コストと所要時間を抑える）の列を見る。
3. 表の記号を推測で補わない。
   - **`同じ`** … 通常推奨と同じ候補でよい**積極的根拠がある**。
   - **`—`** … 差も同一性も裏付けられない。**候補を作らない**（「たぶん違う」で埋めない）。
   - **`（条件 n）`** … 表直下の条件を満たすときだけの候補。**条件が成立しなければ通常推奨へ畳む。**
4. 「指示の型」に従ってプロンプトを組む。詳細な最適化は各モデルの `03/04/05` を参照。

**効率は API 単価だけで決まらない。** トークン量・待ち時間・再実行・手戻りまで含めて評価する（単価の安いモデルが、やり直しが増えれば総コストで負けることがある）。

**タグの意味**：`[Official]` = 公式裏付けあり（source_id）。`[Heuristic]` = プロジェクト運用仮説（Confidence 付き、公式裏付けなし）。

**タグ規律の例外**：下の「タスク別判断表」のセルは読みやすさ優先の無タグ要約（Official と Heuristic の混合）。各行の根拠とタグは「タスク別の根拠内訳」セクションが正式に担保する。

## 判断の土台（公式ポジショニング）

- 迷ったら **Opus 5**（大半のワークロードの既定の出発点。現行逐語は "start with Claude Opus 5 for most workloads"）。`[Official]` S81
- 最高能力が要る、demanding reasoning・long-horizon agentic work、または Opus 5 の高 effort でも evals が届かない → **Fable 5.1**（Anthropic の最も高能力な widely released モデル。Fable 5 の後継）。`[Official]` S122, S123
- 速い対話・高頻度・低コストの主力 → **Sonnet 5**。`[Official]` S11 ／ 「Fable 5.1 は速い対話・高頻度には使わない」は公式事実（比較レイテンシ「Slower」・価格は Opus 5 の 2 倍・長時間セッション前提 — S125）から導く運用判断。`[Heuristic]` / Confidence: High / Basis: S125 の公式事実。
- **Opus 5 は Opus 4.8 に対する step-change で、Fable 系のフロンティア級知能を半額（$5/$25 対 $10/$50。Fable 5.1 も同一価格 — S126）で提供する。** 強みは深い推論・エージェント型コーディングと長時間タスク・test-time compute scaling・低 effort での効率・コードレビュー・vision・long-context・マルチエージェント統率。`[Official]` S83 ／ **ただし「最大の向上は〜」の列挙は Opus 4.8 に対する改善リスト**であり、Fable 系との品質比較ではない。Fable 相対の記述は「フロンティア級知能を半額で」の一句だけで、これは一般ポジショニングである（同じ台帳が S122「最も高能力な widely released モデル＝Fable 5.1」を並置している）。
- **公式はモデル選定の開始アプローチとして 2 方式を提示する**：efficiency-first（より速く低コストなモデルから始める）と capability-first（能力の高いモデルから始める）。`[Official]` S107 ／ **この 2 方式を本判断表の 3 プロファイルへ対応させるのは本プロジェクトの運用判断**であり、公式はこの対応づけを述べていない（公式の efficiency-first は Haiku 4.5 から始める手順で、S66 で 3 モデルに限定した本リファレンスとは出発点が違う）。`[Heuristic]` / Confidence: Medium / Basis: S107 の公式事実＋プロファイル設計という運用判断。
- **model と effort は別の軸（性能ダイヤルの上下ではない）。** model 設定は「どの重みが処理するか」＝おおよそ **how capable（どれだけ有能か）**、effort 設定は「各ターンでどれだけ作業するか」＝おおよそ **how thorough（どれだけ徹底的か）**。effort は「思考時間」だけでなく、ツール呼び出し・応答を含む作業量全体を制御する。`[Official]` S69, S65
- **2 軸は直交する。** 低 effort の大モデルは「専門家に 5 分」（深い経験、ただしざっと読み）、高 effort の小モデルは「優秀なゼネラリストに午後いっぱい」（全部読み、動かし、見直す）。Fable は低 effort でも「一瞥で、他の誰も見抜けない急所を見抜く専門家」（S70 の枠組みはモデルファミリー名で書かれている）。`[Official]` S70 ／ タスクに要るのが**有能さ**か**徹底さ**かを分けて問う（S69, S70 から導く運用指針）。
- **ノブより先に前提を点検する。** Claude が誤ったとき、最初にすべきは model/effort の調整ではなく、渡したコンテキストの点検（プロンプトが曖昧でないか・CLAUDE.md の前提・タスクのスコープ）。不要なはずのタスクで effort を上げているなら、修正はしばしば上流にある。`[Official]` S67
- **ノブを回すなら、まず症状で切り分ける（effort を無条件に先へ上げない）。** ファイルを飛ばした・テスト未実行・見直し不足で誤った → effort を上げる／コンテキストが揃い、明らかに試みたのに誤った → より大きいモデルへ。effort は単一モデル内で知性↔速度/コストを動かせ（low は短い・レイテンシ重視、medium はコスト重視のバランス）、モデル切替より良いレバーであることが多いが、これは切り分けの結果として選ぶもので最上位ルールではない。`[Official]` S6, S65, S68
- **指示は明確・明示的に。** 「上をいく」挙動が欲しいなら明示的に要求する。文脈の乏しい同僚に見せて従えるか、が黄金律。`[Official]` S46
- **effort の既定は high（Claude API・Claude Code とも。`effort:"high"` は省略時と同一挙動）。** `[Official]` S71 ／ モデル別の公式開始点：**3 モデルすべて high（既定）開始**。xhigh へ上げる条件がモデルで違う — **Opus 5 は demanding なコーディング・エージェント作業**（S86）、**Sonnet 5 は最難のコーディング/エージェントタスク**（S74）、**Fable 5.1 は most capability-sensitive な作業（xhigh または max）**（S128）。`[Official]`
- **effort は default-first。** 大半のタスクはモデル既定の effort を使い、タスクごとの自動ルールではなく作業スタイルの一般選好として調整する（S80）。同名 effort はモデル間で同じ内部強度を意味しない——モデルを替えるなら effort も引き直す（S78）。`[Official]`
- **Opus 5 では低い effort の価値が上がった。** low / medium は旧 Opus より強く、evals で品質が保てる範囲ならトークンコストと応答時間の主要な制御手段として積極的に使ってよい。旧モデルから effort 設定を持ち込まず引き直す。`[Official]` S87
- **Opus 5 では effort を下げても表示される応答は短くならない。** effort が制御するのは思考量。長さはプロンプトで明示指定する。`[Official]` S88
- **effort は会話の途中で動かさない。** effort を変えると先行ターンのキャッシュ prefix が保持されない。上げ下げするならセッション開始時に決めて一定に保つ。`[Official]` S120 ／ **例外**：per-message effort 対応モデル（Fable 5.1 / Opus 5）は API 上キャッシュを保ったまま会話中に変えられる（S130）。ただし Claude Code の運用としては開始時に決める原則を維持する。

### プロファイル候補の条件（`（条件 n）` の中身）

**条件の 3 分岐**：成立している → その候補を出す／**成立していない → 通常推奨へ畳んで確定する**（選び直しを求めない）／**判定できない → 候補を出さず、条件を説明して選び直しを促す**。

**成立しなかった／判定できなかったときの表示文**（`<プロファイル>` は「成果優先」か「効率優先」）

| 場合 | 表示文 |
| --- | --- |
| 成立していない | `<プロファイル>は、この依頼では条件を満たさないため通常推奨に畳みました。` |
| 判定できない | `<プロファイル>は条件つきの候補です（<条件の要旨>）。条件を満たすと分かっている場合だけ指定してください。` |

- **既定（high）から動かす行には、必ず公式の昇格・降格根拠を紐づける。** 昇格：コーディング・エージェント作業（S86, S74, S128）。降格：evals で品質維持を確認した場合（S87）、短くスコープされた作業・レイテンシ重視（S65）。根拠のない非既定 effort をこの表に置かない。

- **根拠が無いことを `同じ` にしない。** 「差の証拠がない」と「差がない証拠がある」は別物。前者は `—` である。
