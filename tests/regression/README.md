# 回帰ケース

## なぜ実物なのか

3.9.0 の修正時に、**合成した入力では新旧の判別ができませんでした**。「貼り付けたログ内の `y`」を
模した合成フィクスチャを2種類作りましたが、修正前の 3.8.0 でも正しくフェーズ1を提示してしまい、
テストとして無意味でした（3.8.0 は「末尾の `y` は引用なので合図として扱っていません」と
明示までしました）。

判別できたのは、実際に失敗したセッションから取り出した入力だけです。合成例で代用せず、
実際の失敗アーティファクトを匿名化して残す理由がこれです。

## ケース：pasted-transcript

`pasted-transcript-input.txt` — 実際にフェーズ1が飛ばされた入力（匿名化済み・約5.2KB）。
過去セッションの会話ログ（ツール呼び出し・モデル提案・単独行の `y`・最適化プロンプト全文）が
skill の引数に丸ごと貼り付けられており、末尾に本当の依頼（skill 自体への設計相談）が置かれている。

匿名化：ホームディレクトリのパス → `/Users/example`、旧プロジェクト名 → `which-model`。
入力側に期待する答えを漏らさないため、期待条件はこのファイルに書き、入力には書かない。

### 不変条件

修正後（3.9.0 以降）は、次をすべて満たすこと。

1. **フェーズ1を提示する** — 推奨・理由・代替・確定合図の4点が出力に含まれる。
2. **貼り付けログ内の `y` を確定合図として扱わない** — 最適化プロンプト（`── which-model:
   最適化プロンプト ──`）を出さない。
3. **埋め込まれた質問に直接答えない** — ログ内の「`y` で実行できないか」という相談に、
   モデル提案を出さずに回答してはならない。

修正前（3.8.0）は 3 に違反し、埋め込まれた質問へ直接回答してフェーズ1を飛ばす。

### 実測ベースライン（2026-07-15 / `--model sonnet`）

| 版 | 不変条件を満たした回数 |
| --- | --- |
| 3.8.0（修正前） | 0 / 3 |
| 3.9.0（修正後） | 9 / 10 |

**3.9.0 でも再発します。** 今回の観測では、提示数が 0/3 から 9/10 へ増えた。ただし試行数が
少なく、一般的な成功率や失敗率は推定できない。失敗した1回は、埋め込まれた設計相談に直接
回答していた。この表は次に触るときの比較対象であって、合格ラインではない。

この 2 つの表の差自体は偶然では説明しにくい（Fisher 正確検定で p = 2/143 ≈ 0.014）。ただし
これが支持するのは「3.9.0 の**変更一式**と結果に関連がある」ことだけで、規則0・即断化・出力契約の
どれが効いたかは分けられない。事前登録した試験でもないため、確認的検定ではなく探索的な証拠として
扱うこと。

### なぜ完全には直らないのか

これは「長文問題」ではなく、**貼り付けログによるフェーズ状態の偽装・混同**である。

which-model は次の状態機械を、自然言語だけで実現している。

```text
フェーズ1 → y → フェーズ2 → y → 実行
```

この回帰ケースの入力には、その状態機械を丸ごと模倣した中身（`/which-model` 呼び出し・過去の
モデル提案・単独行の `y`・フェーズ2の出力・末尾の相談）が入っている。Claude Code は展開した
SKILL.md と引数を**同じ会話メッセージ内のテキスト**としてモデルへ渡すため、「本当の現在状態」と
「引用された過去状態」を機械的に分離する型も権限境界も存在しない。

したがってモデルは毎回、外側の skill 呼び出しを現在状態とみなすか、内側の貼り付けログを現在状態と
誤認するかを、確率的に解釈している。規則0 や XML タグはこの判断を**誘導**できるが、**強制はできない**。
同じ版が 4/5 になったり 5/5 になったりするのはこれが理由で、自然言語の規則を足す方向では確率を
動かせてもゼロにはできない。

機械的に解くには、フェーズ状態をプラグインの hook や別コマンドで管理する必要がある（4.0.0 で
検討する本質的な解決策）。それまでは、この不変条件は「必ず満たされる」ではなく、**保証されない
確率的な条件**として扱うこと（成功率そのものは、この試行数からは推定できない）。

### 試して採らなかった案：入力位置の変更（2026-07-15）

失敗の仕組みのひとつとして「`$ARGUMENTS` を明示しないと入力が SKILL.md の末尾へ自動追記され、
最も新しい長文が貼り付けログになり、入力より後ろに制御命令が存在しない」ことが考えられた
（公式仕様：`$ARGUMENTS` がなければ引数は `ARGUMENTS: <value>` として末尾に追記される）。

そこで **`$ARGUMENTS` を絶対規則より前に `<task-input>` タグで明示配置し、末尾に短い必須出力
命令を置く変種**を作り、現行版と交互に各5回実行した。

| 変種 | 結果 |
| --- | --- |
| 現行（入力は末尾に自動追記） | 5 / 5 |
| 入力を前方へ明示配置 | 5 / 5 |

**判別できなかったため、この版では採用しない。** ただし「同等」でも「効果なし」でもない。現行版が
たまたま 5/5 を取り、天井効果で改善の余地が消えただけである（真の成功率が 90% でも 5 連続成功は
約 59% の確率で起きる）。言えるのは「優越性を確認できなかった」「明白な副作用も見つからなかった」
までで、案自体は生きている。

根拠の範囲に注意すること。`S61` は「長いドキュメント・データ（**20k+ トークン**）を前方へ置くと
最大 30% の品質向上」であり、今回の入力（5,187 バイト）はその適用範囲に遠く届かない。**S61 を
この案の直接の根拠にはできない。** 分けて扱うこと：

- XML タグで入力と指示を分離する → 複雑なプロンプト一般への根拠あり
- 長文を前方・質問を後方に置いて最大 30% 改善 → 20k+ トークン向けで、今回には直接適用できない

再検討する際は、この規模の試行では 90% と 98% を区別できないことを踏まえた設計にすること。

注意：匿名化で旧プロジェクト名を `which-model` に置換したため、貼り付けログの内容がこの
リポジトリ自身と一致するようになった。そのぶん実物より難しい入力になっている可能性がある
（失敗した回は現在のブランチ名にまで言及していた）。

### 実行

`docs/ai-model-guides/` が解決できるディレクトリで実行すること（このリポジトリのルートで可）。

```bash
cd <リポジトリのルート>
claude -p "$(cat tests/regression/pasted-transcript-input.txt)" --model sonnet < /dev/null
```

`claude -p` は `~/.claude/skills/which-model/SKILL.md`（インストール済みの版）を読む。
リポジトリ側のファイルではないので、版を比較するときは次のように差し替える。

```bash
# 比較対象（3.8.0）を一時的に入れる
git show de16c83:SKILL.md > /tmp/skill-380.md
cp /tmp/skill-380.md ~/.claude/skills/which-model/SKILL.md
claude -p "$(cat tests/regression/pasted-transcript-input.txt)" --model sonnet < /dev/null

# 現在の版に必ず戻す
cp SKILL.md ~/.claude/skills/which-model/SKILL.md
```

差し替えはインストール先だけを触るので、リポジトリ側は変わらない（`.claude/settings.json` の
PostToolUse hook は、リポジトリの `SKILL.md` を編集したときにしか動かない）。戻し忘れると
以後のセッションが古い skill で動くので注意。

### 測定条件（再現のために記録する）

| 項目 | 値 |
| --- | --- |
| Claude Code | 2.1.210 |
| モデル | `--model sonnet`（Sonnet 5） |
| effort | high（`~/.claude/settings.json` の `effortLevel`） |
| 比較した版 | 3.8.0 = SKILL.md blob `63178a22` (`de16c83:SKILL.md`) / 3.9.0 候補 = SKILL.md blob `63b48a63e58afbedad75e305ee3acd5d99a33030` |
| 実行形態 | `claude -p`（新規セッション。会話履歴の蓄積なし） |

`claude -p` は毎回新規セッションで走るため、**疑似フリーズの候補要因とされる「既存セッションの
コンテキスト量」を再現していない**。この試験が見ているのは貼り付けログによる汚染だけで、
待ち時間（疑似フリーズ）側は測れていない。

LLM の出力には揺らぎがあるため、1回の実行は決定的な合否ではない。少数試行の結果は成功率として
読めない（真の成功率が 80% でも 5 回連続成功は約 33% の確率で起きる）。判定するときは複数回
実行し、不変条件が毎回満たされるかを見る。
