# VS Code 拡張：長い入力の直後に応答が描画されない件（実測記録）

6.0.0 で選択UI化と合図分離（`p`＝表示・`g`＝実行）を決めた根拠。**これは拡張側の不具合であり、この skill の
受入条件ではない**（受入条件は [`README.md`](README.md) の「6.0.0 の受入条件」）。

## 測定条件

| 項目 | 値 |
| --- | --- |
| 日付 | 2026-08-11 |
| VS Code 拡張 | 2.1.226 および 2.1.227（両方で再現） |
| 対話ターミナル | 2.1.220 / 2.1.227（いずれも再現せず） |
| OS | macOS（Darwin 25.5.0） |
| 表示 | 外部ディスプレイ、論理解像度 3008 × 1692（UI looks like） |
| 計測器 | 使い捨てスキル `wm-text-test`（引数を分類せず、目印のテキスト1ブロックだけ出して停止する）。実体とペイロード生成器は [`instruments/`](instruments/) に保管 |
| 手順 | 1回につき新規会話。ペイロードを貼って送信し、目印ブロックが画面に出たかだけを記録 |

**なぜ専用の計測器が要ったか**：`/which-model:pick` 自体で測ると、判定内容・応答長・所要時間が
毎回変わって交絡する。引数を読まず固定長のテキストだけ返すスキルにすることで、変数を
「入力の見た目」だけに絞った。

## 測定1：文字数・バイト数は引き金ではない

| 文字 | UTF-8 バイト | 結果 |
| ---: | ---: | --- |
| 16 | 30 | 表示 |
| 950 | 2,840 | 表示 |
| 1,250 | 3,738 | 表示 |
| 1,400 | 4,188 | 表示 |
| 1,550 | 4,638 | 表示 |
| 2,500 | 7,488 | 表示 |

いずれも改行のほぼ無い一段落。**旧説の「4,391 バイトで不可視」を大きく超えても表示された。**

## 測定2：行数が引き金（総文字数 2,500 を固定）

| 文字 | バイト | 行数 | 結果 |
| ---: | ---: | ---: | --- |
| 2,500 | 7,488 | 1 | 表示 |
| 2,500 | 7,400 | 40 | 表示 |
| 2,500 | 7,360 | 60 | 表示 |
| 2,500 | 7,340 | 70 | 表示（画面1枚に収まっていた） |
| 2,500 | 7,320 | 80 | **不可視** |
| 2,500 | 7,158 | 160 | **不可視** |

文字数は完全に同一、バイト数もほぼ同一（改行は1バイト）。**違うのは行数だけ。**
この条件での境界は 70〜80 行。

## 測定3：真の変数は「画面1枚に収まるか」

ペイロードを一切変えず、**ウィンドウの高さだけ**を約半分にした。

| 行数 | ウィンドウ高さ | 1画面に収まるか | 結果 |
| ---: | --- | --- | --- |
| 60 | 通常 | 収まる | 表示 |
| 60 | 約半分 | 収まらない | **不可視** |

同一ペイロードで結果が反転したので、**引き金は入力の中身ではなく、貼り付けブロックの描画高さが
ビューポートに収まるかどうか**である。行数が効いて見えたのは、行数が高さの代理変数だったため。

## 併せて確認した事実

- **生成・保存は正常。** 不可視だったケースでも、応答は text ブロックとしてセッションの JSONL に
  保存され、`end_turn` まで完了していた（例：セッション `670e81f2`、VS Code 2.1.227、
  引数 8,345 文字／18,433 バイト、回答受領 04:35:16 → 応答生成 04:35:21）。
- **スクロールでは戻らない。** 最下部まで移動しても現れなかった。
- **会話を開き直しても戻らない。** 履歴再生でも現れなかった。よって「ライブ描画だけの取りこぼし」
  でもない。
- **確認できた復帰方法は、新しい短いメッセージを送ることだけ。**
- 対話ターミナルでは同じ 9,621 文字のペイロードで再現しなかった。

## 閾値の導出（32 行は実測値ではない）

`SKILL.md` が使う「推定表示行数 32 行」は**外挿であって実測境界ではない**。導出は次のとおり。

1. 実測境界は 70〜80 行（論理解像度 3008 × 1692 の外部ディスプレイ、ウィンドウ最大化）。
2. 上下の固定部分（タイトルバー・ステータスバー・入力欄）を約 150 ポイントと仮定し、
   13〜14 インチのノート（縦 956〜982 ポイント）へ比例換算すると約 38〜43 行。
3. サイドバー配置・フォントサイズ変更・エディタ分割の余地を見て、そこから約 25% 引いて 32 行。

**13〜14 インチでの実測は行っていない。** 手順2の仮定（固定部分 150 ポイント、比例スケール）は
未検証である。ただしこの数値が決めるのは「`p` が必須か保険か」だけで、機能の成否ではない
（選択UIには常に「表示されない場合は `p` を送ってください」と書いてあるため）。外した場合の
損失は、警告文の強弱と `p` が1回増えるかどうかに留まる。

## 上流

近い報告は [anthropics/claude-code#61675](https://github.com/anthropics/claude-code/issues/61675)
（open、`stale` ラベル、milestone なし。約 4,000 文字域で後続メッセージが隠れるという内容で、
本件と同族と見てよい）。**2026-08-12、この文書の測定結果を同 issue へ投稿した**
（[コメント](https://github.com/anthropics/claude-code/issues/61675#issuecomment-5260948384)）。
既存の報告はいずれも文字数で語っているため、**文字数ではなく描画高さが引き金である**という
対照実験（ペイロードを変えずウィンドウ高さだけを半分にして結果が反転した測定）が新規の寄与になる。
新規 issue は立てていない（報告が分散するため）。`AskUserQuestion` まわりの類似報告として
[#85573](https://github.com/anthropics/claude-code/issues/85573)（fullscreen TUI で回答後の
継続ターンのテキストが描画されない）、
[#84065](https://github.com/anthropics/claude-code/issues/84065)（`AskUserQuestion` 直前の
テキストが描画されない）がある。**条件は同一ではないため同一原因とは断定しない**が、
「`AskUserQuestion` と同じターンに置いた重要なテキストは複数の UI 経路で不可視になりうる」
という判断の根拠にはなる。6.0.0 が重要な本文を別ターンへ分けているのはこのためである。
